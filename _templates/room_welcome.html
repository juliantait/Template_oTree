{# THE ROOM WELCOME GATE — the study's own styling on oTree's entry interstitial. WHAT THIS PAGE IS. oTree 6 serves an interstitial on every room entry: a GET on /room/ WITHOUT `welcome_page_ok=1` renders this template instead of admitting the participant (otree/views/participant.py:289-292). It is new in oTree 6 — oTree 5 had no such page — which is why it is not in anyone's memory of the older lab studies. Stock, it is bare framework markup: a flush-left `Welcome`, "Click the button to start", Bootstrap. It is the FIRST THING a participant sees, and it looked like a different piece of software from the study behind it. WIRED VIA `welcome_page` on the ROOMS entry in settings.py — oTree renders `room.welcome_page or "otree/RoomWelcomePage.html"`. Same mechanism and same file location as exp_pilots uses, so the two studies stay comparable. =================================================================== STYLING ONLY. THE SCRIPT BELOW IS oTree's, VERBATIM, AND IS THE PAGE'S MECHANISM — DO NOT "TIDY" IT. =================================================================== The submit handler is not decoration: it preventDefaults, POSTs the fields for validation, and only then reloads with `welcome_page_ok=1`, which is what admits the participant. Copied byte-for-byte from oTree 6.0.15's `otree/templates/otree/RoomWelcomePage.html` so it can be re-diffed on an oTree upgrade; only the MARKUP AROUND IT is ours. Its DOM contract is `form`, `input[name="participant_label"]`, `[data-field-error=…]` and `#other-errors` — every one of those is still here. NO SKIP OR AUTO-SUBMIT BEHAVIOUR IS IMPLEMENTED HERE, deliberately. Making the gate self-submit when the URL carries a participant id is a SEPARATE OPEN DECISION (and carries the `form.submit()` vs `requestSubmit()` hazard recorded in CLAUDE.md — `form.submit()` does not fire submit listeners, so it would bypass the very handler below and loop the page forever). This file changes how the gate LOOKS and nothing about what it DOES. WHY NO CREED HEADER, AND NO MENTION OF PROLIFIC. This page is reachable in BOTH recruitment modes — the lab enters through the room, and the Prolific participant link is `/room/?participant_label=…` (see docs/hosting_a_prolific_study.md) — and oTree renders it with a context of ONLY `has_participant_label_file`: no session, no config, no `recruitment` value. So the template CANNOT branch on study type even if we wanted it to, and the two-variants rule resolves the only way it can: copy that is true in both modes, naming neither. `welcome_header.html` (Welcome to CREED) is therefore deliberately NOT included — it is lab-only by its own contract, and a Prolific participant must never see it. WHY base.css IS LINKED DIRECTLY RATHER THAN VIA css_bundle.html. The bundle is `{% include %}`-ed by oTree PAGES and needs page context this render does not have: `{{ C.STATIC_VERSION }}` for its cache-buster, and it pulls in tabmonitor_assets.html, which belongs to a monitored page inside a session — neither exists here. base.css alone carries every class this page composes (.experimental-screen, .screen-card, .narrative-card, .experimental-content, .section-text, .button-row, .next-button, .logo-section); the other bundle files only override those for specific pages. The cost is that this one link carries no `?v=` — see settings.ROOMS for the note. #} Welcome
