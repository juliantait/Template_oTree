{# THE ROOM WELCOME GATE — the study's own styling on oTree's entry interstitial. WHAT THIS PAGE IS. oTree 6 serves an interstitial on every room entry: a GET on /room/ WITHOUT `welcome_page_ok=1` renders this template instead of admitting the participant (otree/views/participant.py:289-292). It is new in oTree 6 — oTree 5 had no such page — which is why it is not in anyone's memory of the older lab studies. Stock, it is bare framework markup: a flush-left `Welcome`, "Click the button to start", Bootstrap. It is the FIRST THING a participant sees, and it looked like a different piece of software from the study behind it. WIRED VIA `welcome_page` on the ROOMS entry in settings.py — oTree renders `room.welcome_page or "otree/RoomWelcomePage.html"`. Same mechanism, same file location and the same auto-pass behaviour as exp_pilots, so the two studies do not drift. =================================================================== WHAT IS OURS AND WHAT IS oTree's — READ THIS BEFORE EDITING THE SCRIPT. =================================================================== The page now does TWO things: it wears the study's styling (all of the markup above), and it AUTO-PASSES a visitor whose URL already identifies them (Julian, 2026-08-14 — this replaces an earlier "styling only, no auto-submit" state of this file). The script is in three marked parts: PART 1 (OURS) read the id from the URL, and decide whether to auto-pass. PART 2 (oTree) the submit handler, VERBATIM from oTree 6.0.15's otree/templates/otree/RoomWelcomePage.html. It preventDefaults, POSTs the fields for validation, and only then reloads with `welcome_page_ok=1` — which is what actually admits the visitor. Re-diff it on any oTree upgrade. DO NOT "TIDY" IT. PART 3 (OURS) fire the auto-pass, AFTER part 2 has bound its listener. THE RULE THAT MAKES THIS SAFE, AND THE ONE THAT WOULD BREAK IT: * `form.requestSubmit()`, NEVER `form.submit()`. `submit()` does not fire submit-event listeners, so it would bypass PART 2 entirely: no gate POST, no `welcome_page_ok`, and the browser reloads the same URL — which auto-passes again, forever. And it would do that ONLY for arrivals carrying an id, i.e. only for real participants and never once while anybody tests with a bare URL. `requestSubmit()` fires the handler, which is the whole point of using it. * NO SLOT IS CLAIMED WITHOUT A CLICK when the URL carries no id. That is load-bearing, not a nicety: a bot arrives with no id and usually runs no JavaScript, so the button is what keeps it out. Do not auto-pass a bare URL "for convenience". * THE LOOP GUARD. Auto-pass happens at most ONCE per tab (a sessionStorage timestamp, 30s window). If we are back on this page inside that window, the previous attempt did not admit us, so we show the button instead of trying again — a failure a participant can click through is recoverable; a failure that retries is a participant who never arrives and leaves no trace. If sessionStorage is unavailable, or the browser has no `requestSubmit`, we do NOT auto-pass at all: without the guard the safe answer is the button. WITH JAVASCRIPT DISABLED nothing here runs, so an id-carrying arrival sees the styled page — and CANNOT get past it, because PART 2 is the mechanism and it is JavaScript.
